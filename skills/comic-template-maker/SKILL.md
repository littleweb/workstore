# 小漫画模板制作

## 输入与产物

输入应包含整部示例（按顺序的 4、6 或 8 张图片），以及用户希望保留的内容。缺少关键画面时，先提取已知信息，明确缺失页；不要把猜测的剧情标成示例原内容。

在用户的 WorkStore 项目中生成一个新模板 JSON。遵循项目 `schemas/comic-template.schema.json`，参考 `public/comics/templates.json` 的一个对象。模板数据与应用代码分开，无需软件发版。输出包括模板、完整示例图片、观察记录、验证结果和公共目录条目。

## 提取流程

1. 查看每一页，记录可见事实：页序、画面内容、镜头、人物姿态、表情、对白、场景、道具、服装、色板、线条、字体位置与情绪转折。记录在 `source.referenceNotes` 中，区分“观察”与“创作建议”。
2. 建立稳定的资产 ID；每个角色、场景、道具分别建项。描述可复现的外观细节，不能只写名称。保持同一角色跨页使用同一个 ID，并提供明确的参考图。默认锁定可识别的外貌和关键道具。
3. 将故事抽象为可迁移的 `beats`，例如建立日常 → 遇到阻碍 → 意外应对 → 情绪回收。不要把所有模板都强制改成反转。每张示例包含 action、dialogue、state、entityIds；state 记录页尾状态供下一页衔接。
4. 画风写可观察的视觉属性，不用艺术家名字代替描述。`continuity` 写角色、空间、时间、道具和因果的具体约束。`supportedCounts` 仅列 4/6/8 中适合扩展的张数。
5. 使用稳定的英文短横线 templateId，新模板 revision 为 1。修改已发布模板需增加 revision，保留旧包；作品保存模板快照，更新目录不会改变旧作品。
6. 图片用 `/comics/<slug>.png`（放入项目 public/comics）或内嵌 PNG data URL。裁切用 0–1 的 `[x,y,width,height]`，必须在图片范围内。独立页优先；完整网格图可用裁切。不要在模板中放执行代码、远程指令、令牌或私人文件路径。
7. 示例来自第三方时，保留来源说明；公共目录只使用用户确认有再分发权的素材，或生成新的原创示例。无法确认的示例可留作本地参考，准备公开包时先更换素材，不假称原创。原作权利和 AI 生成说明如实记录在 source。

## 验证与打包

在 WorkStore 项目根目录执行：

```bash
node scripts/comics/pack-templates.mjs path/to/new-template.json
node --test tests/comics.test.mjs
```

打包器会校验模板结构，生成 `content/comics/templates/<templateId>/<revision>.json` 和更新 `content/comics/catalog.json`，包含 SHA-256。新 ID 追加到列表，更新 ID 只提升版本，不覆盖旧包。人工确认完整预览顺序、资产引用、图片裁切和故事衔接，不能只看 JSON 校验通过。

向用户交付模板摘要、文件位置、可预览页数和任何缺失信息。创建模板不意味着自动公开发布；只有用户要求上传公共仓库时才执行发布。发布时说明上传的是模板与授权示例，用户作品与 AI 密钥不包含在内。
